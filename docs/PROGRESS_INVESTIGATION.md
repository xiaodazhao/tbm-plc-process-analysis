# 进尺读数的证据调查

## 本轮范围

这是当前日报事实层中的一个有边界的调查工具，不是通用Agent、故障诊断器或距离修复算法。复用已修复PLC样本、推进状态、平台归属和真实支持时长，不重跑或修改冻结的四阶段算法。旧日报及历史实验保持不变。

## 实际执行顺序

`pipeline.prepare → enrich_front → enrich_progress → investigate_progress → apply_report_decisions → unified_report_input.json → Planner/Generator/Editor → 既有核验与渲染`

`scripts/investigate_progress.py`另提供无API的历史回放。它使用已有三天报告中的真实样本，逐行比较标准化CSV的开累进尺与盾首里程，保存调查JSON、人工空白核查表、上下文CSV、检查图及未发送规划请求。它不是另一个日报生成入口。

## 程序完成的判断

1. 相邻有限累计读数大于原配置正跳阈值或达到原配置回退阈值时，建立调查。阈值继续读取`configs/daily_report_front_sections.json`，目前均为0.5m，不修改原算法配置。
2. 单个连续观测区间中，累计读数基本不变，同时存在累计至少600秒的推进支持、有效非负速度覆盖不少于80%、推进速度中位数大于0.5mm/min时，建立“推进记录与累计读数不一致”调查。
3. 用真实时间差和原支持时长限制连续性，缺失值、硬缺口、跨源文件和超过60秒间隔均切断恒值区间。末记录的支持不计入恒值区间。长间隔两端差值只记录为跨缺口变化，不表述为瞬时推进。
4. 只有恒值区间后紧接连续正跳、盾首在恒值期间也不更新且在同一记录对正向变化、盾首质量标记可用时，才提出“延迟或集中更新”的候选解释。
5. 影响范围与观察范围分开：某平台恒值期间的有效推进支持至少600秒，才按此规则暂缓该平台进尺。突跳只有发生在同一平台内部才直接归属给该平台；平台边界的变化不随意分摊。
6. 报告层保留每项旧值、原质量判断及原因，再将受影响分段进尺和效率置为暂不采用。原始平台结果、原始数据、日进尺与日状态时长不改动。

600秒、80%、60秒等是透明可配置的描述筛选参数，不是仪器标准、安全阈值或已验证的最优参数。所有参数随调查结果保存。参数变化需要新输出目录，不因某个日期结果好看而偷偷调参。

## 模型的职责与限制

调查结果先成为2.2节有独立ID、来源SHA及解释边界的事实，之后才供LLM进行内容选择和写作。涉及所选主要活动的调查为必需事实；其他调查允许有理由地省略。模型不负责发现数值突跳、不计算时长、不分配距离。

正文检查新增有限的防护：无对应调查不能自行增加“延迟更新”解释；有候选证据也必须保留可能/疑似；不能宣称通信故障、已修复或已分摊距离。累计读数与读数跳变量按来源允许显示，不冒充已采用的分段进尺或m/h。此检查仍是有限词法和数值检查，不能保证识别所有同义改写；未核查的工程语义继续为REVIEW，不声称获得真实事实准确率。
