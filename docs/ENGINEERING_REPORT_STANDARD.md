# 三章工程日报统一发布标准

## 现在采用的顺序

1. 第一章：当日施工总体情况，保留已认可的概况，不临时扩写。
2. 第二章2.1：全天运行概况。说明全天进尺、累计推进时间、推进时间占有效记录的比例、全天折算推进率；用简洁参数表和全天真实曲线呈现整体水平。
3. 第二章2.2：主要掘进区间。沿用已有活动组及代表性选择，不重新分段。用四列表列出主要时段、累计推进时长、平台内进尺、折算推进率；文字突出贡献和真实局部运行表现，不重复表的每个数字。选中几个局部窗口，就分别绘制几张图，每张包含速度、推力、扭矩三个独立纵轴。
4. 第三章：保留上游已核查的地质—机器描述、历史揭示和前方20米预报；不在发布层重新判断地质。正文用“里程”，不因改术语而假定盾首就是掌子面。

第一章和第三章使用此前已通过检查的文字，本轮不让第二次LLM擅自重写。上游仍可使用整份三章联合规划/生成；发布层是统一风格和图文展示的最后一步，不是另一次地质分析。

## “效率”具体指什么

| 名称 | 分子 | 分母 | 含义 |
|---|---|---|---|
| 全天折算推进率，m/h | 有质量依据的日导向盾首首末差 | 当天已识别推进状态累计小时 | 日完成量按有效推进时间折算 |
| 主要区间折算推进率，m/h | 该组各运行平台内部“开累进尺”净变化合计 | 同一组平台内推进状态累计小时 | 所选活动的PLC进尺与推进时间关系 |
| 推进时间占比，% | 当天推进状态累计秒 | 有效状态记录累计秒 | 已观测时间中的推进比例 |

这些都不是设备综合效率等级、刀具效率或地质效率，不以某个数值判断好坏。不同区间未必处于同工况。稳定推进速度中位数的单位为mm/min，样本口径也不同，不能用它代替上述折算率。

使用已保存的真实`sample_dt_seconds`，沿用原报告的末条/缺口无支持记录贡献零秒规则，不补成20秒。活动首末跨度不是累计推进时长。

逐平台复用已有`interval_advance`质量状态，再对原始行号及首末差进行回放核对。任一组成平台的进尺待核实、为负、单位/端点不一致，则该活动进尺填“待核实”，折算率不填；不把剩余平台的部分和冒充完整进尺，也不补零。可靠的零进尺可显示为零；无有效推进时间时不做除法。

所有平台边界前后变化只记入审计，不自动分给该平台。各平台内部进尺之和与日盾首里程差来自不同字段，保留对账差异，不强行相等。显示保留两位小数，计算用未取整值。

## 固定展示和文字要求

- 白底、中文正文10.5pt，实际PDF检查字号；不为了页数压小字体。
- 每个主要时段保留真实边界；表和图由Python生成，不让模型写表格或图点。
- 局部窗口正文只写准确时间和已有趋势/联合方向；样本数、支持时长、四分之一统计留在审计文件。
- “未检出持续趋势”不等于参数波动小，不可自动写成“基本稳定”。
- 原图片图3、4、5按JSON现场照片顺序使用，校验文件和日期。历史照片不得标成当天新增揭示；原资料缺失则停止对应照片展示，不补图。
- 缺少当时可用预报，写明覆盖不足，不写成没有岩性、水或风险。
- 限制尽量集中为清楚的口径和来源说明，不逐段堆“不能、不代表”。
- 程序可按精确白名单去掉模型重复的两个章节标题或“各窗口真实局部曲线另行插入。”这种纯编写占位句，保存改动记录。不能删除工程事实句来通过检查。

## 唯一标准发布入口

```bash
python scripts/run_three_chapter_report.py publish --bundle /one/completed/day --output /new/output --offline
python scripts/run_three_chapter_report.py publish --bundle /one/completed/day --output /new/output_with_model
```

每次输出必须是新目录，禁止覆盖历史报告。`--offline`不读密钥、不调用API。正常发布最多一次生成和一次针对检查错误的反馈，不无限重试；失败保留原始回复和错误，没有合格PDF就明确失败。

支持的材料格式：

- 已有单日展示包：`original_case.json`、`narrative.revised.json`，以及原事实JSON（可用`--facts`显式指定），照片追溯文件如有则读取。
- 标准单日分析包：`report_facts.json`、`evidence_pack.json`、`content_plan.json`、`narrative.json`及`figures/parameters_focus.png`。不在多个日期或A/B组里自动搜一个“成功”结果替代指定输入。
- 可用`--approved`显式指定已认可正文。未更新的旧素描路径/哈希应先重新准备事实，不静默猜测来源。

主要维护位置：

| 文件 | 职责 |
|---|---|
| `configs/engineering_report_standard.json` | 固定发布契约与验收要求 |
| `tbm_process/reporting_v2/activity_facts.py` | 复用原平台、时间、进尺质量及稳定样本，计算可追溯的活动事实 |
| `tbm_process/reporting_v2/publication.py` | 标准输入、DeepSeek文字组织、检查、固定HTML和PDF |
| `tbm_process/reporting_v2/engineering_presentation.py` | 共享真实窗口图、来源和成品检查；保留旧实验的只读复现助手 |
| `scripts/run_three_chapter_report.py publish` | 当前标准发布入口 |

`prepare`现在优先读取合并后的最新素描JSON，而不继续沿用数据库里已移动的旧路径。SQLite仍只读，日期准入由已有规则判断。旧A/B实验、六章工具和归档报告保留研究用途，不能把它们的原样PDF当成本标准已验收的成品。

## 每次发布的检查

检查PLC来源SHA、同日输入、平台成员不重复、进尺端点/原行号、推进时间分母、缺失支持、数值与单位角色、区间数值归属、窗口时间和方向、绑定ID及成品文字/表格/图片。PDF需检查字号、页内边界及所有表行，图像检查另记结果。

这些检查让不合格结果显式停住，不能保证任何日期的模型措辞一次达到主观审美要求，也不等于工程事实经过独立专家确认。数据缺失或原资料冲突必须显式保留；不以强写结论、忽略失败或无上限重试维持“每次成功”。
